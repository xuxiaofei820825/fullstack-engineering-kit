# 规范驱动的代码审查闭环

本流程用于代码审查，以及任何代码修改完成后的最终检查。审查依据是入口 `SKILL.md` 按变更范围选出的现有规范；本文只规定如何执行审查，不重复前端、后端或跨端规范。

## 确定审查基线

审查前先获取本次任务的完整变更，包括已暂存、未暂存和新增文件，并结合需求确认变更边界。不要只审查最后一次补丁，也不要把工作区中与本任务无关的用户变更误算为本次修改。

根据入口的路由规则列出全部适用规范：

- 所有变更都适用共享工程工作流。
- 后端变更加载全部与实际代码、数据、安全、测试和交付范围相关的后端规范。
- 前端变更加载全部与实际代码、测试、目录、联调和交付范围相关的前端规范。
- API、数据模型或跨端行为变化同时加载两侧的相关规范和集成规范。

审查清单以已加载的规范为准。某项规范不适用时可以跳过，但必须能根据变更内容说明原因；不得因未加载规范而漏检。

## 执行审查

逐项核对适用规范，并检查规范之间的组合影响。至少覆盖业务正确性、架构与依赖边界、API 和数据契约、权限与敏感信息、事务和并发、错误与可观测性、用户可见状态、测试、迁移、兼容性、可维护性及交付要求中实际适用的部分。

每个发现必须是可执行的问题，并包含：

- 严重程度；
- 文件及代码位置；
- 可复现或可定位的证据、实际风险；
- 对应规范文件和章节标题；
- 期望的修复结果。

不要把个人偏好当作规范问题。未被现有规范直接规定、但确实影响正确性或安全性的缺陷，可以作为通用工程问题报告，并明确标记其依据不是仓库规范。

## 修复并重新审查

发现属于任务范围的问题后：

1. 修复所有未解决的问题，不得静默忽略。
2. 重新运行受影响的类型检查、lint、测试、编译或构建。
3. 更新完整变更集，再次按全部适用规范进行审查。
4. 修复引入新变更时，继续重复验证和完整审查。

重新审查必须覆盖完整变更，因为修复可能影响其他文件、契约或规范项。不得仅检查上轮问题所在的代码片段。

## 退出条件

只有同时满足以下条件才能认为审查通过并声明任务完成：

- 已识别并加载全部适用规范；
- 已依据这些规范完成对完整变更的最新一轮审查；
- 最新一轮审查没有未解决的规范问题或通用工程问题；
- 修复后的必要验证全部通过；
- 没有未说明的跳过项、未验证项或已知风险。

环境限制、外部依赖、需求歧义或权限不足导致某项无法验证时，记录具体未验证项、原因和影响，不得声称完整审查已经通过。重复检查无法消除同一阻塞时应停止循环并报告阻塞，而不是无限重试。
